## F-01: конкатенация недоверенного ввода в SQL запроса поиска

- Источник и версия объекта: Semgrep CE 1.175.0, `docs/s09/raw/semgrep-before.json`, конфигурация `semgrep.yml`, область `src`, commit `1802bbf`.
- Указатель: `sql-commandtext-concat` и `sql-commandtext-assignment`, `src/NotesApi/NotesRepository.cs:48` (оба правила указывают на одно присваивание, дубль связан здесь).
- Заявленный риск: нарушение конфиденциальности заметок, запрос одного владельца может вернуть заметки другого.
- Применимость и достижимость: значение `q` приходит из query string обработчика `GET /notes/search` в `Program.cs:16`, значение `owner` из заголовка `X-User` там же, оба попадают в текст запроса без привязки параметра. Обработчик доступен без аутентификации, ограничений на содержимое `q` нет. Проверено фактически: запрос `q=%' OR 1=1 -- ` с заголовком `X-User: alice` вернул 200 и две записи, вторая с `owner: bob`.
- Статус анализа: подтвержден.
- Обоснование и приоритет: высокий. Структура запроса управляется вводом клиента, те нарушается разделение данных и кода запроса. Ограничение условия `owner = ...` снимается payload-ом, последствие это чтение чужих заметок через штатный публичный маршрут.
- Решение и состояние: исправлен, подтверждено повторной проверкой. Негативный тест до правки падал на `Assert.DoesNotContain()` в `tests/NotesApi.Tests/NotesTests.cs:65` (`всего: 5; сбой: 1; успешно: 4`), после правки итог `всего: 5; сбой: 0; успешно: 5`. Повторное сканирование той же области дало 7 сигналов вместо 8, узкое правило на строке 48 молчит.
- Ответственный и следующий шаг: M1, закоммитить изменение и отчеты отдельными шагами, чтобы история показывала последовательность.
- Свидетельства: AVC-01, `docs/s09/raw/semgrep-before.json`, `docs/s09/raw/semgrep-after.json`, `docs/s09/raw/source-after.json`, изменение в `src/NotesApi/NotesRepository.cs`.
- Остаток и пересмотр: после параметризации значение `q` остается шаблоном `LIKE`, символы `%` и `_` внутри него работают как подстановочные. В пределах своих заметок это расширяет выборку, выхода за `owner` не дает. Пересмотреть, если поиск начнет отдавать данные других владельцев или если по шаблону будут считаться метрики.

## F-02: присваивание SQL в трех местах с литеральным текстом запроса

- Источник и версия объекта: Semgrep CE 1.175.0, `docs/s09/raw/semgrep-before.json`, та же конфигурация и область, commit `1802bbf`.
- Указатель: `sql-commandtext-assignment`, `src/NotesApi/NotesRepository.cs:27`, `:35`, `:59` (после правки `Search` последняя строка сдвинулась на `:62`).
- Заявленный риск: правило просит просмотреть любое присваивание текста SQL, тк там может оказаться недоверенный ввод.
- Применимость и достижимость: в строке 27 это `CREATE TABLE IF NOT EXISTS` с постоянным текстом, в строке 35 это `SELECT COUNT(*)` с постоянным текстом, в строке 59 это `INSERT` с именованными параметрами `$o`, `$g`, `$t`, значения передаются через `AddWithValue`. Ни в одном из трех мест в текст запроса не попадает значение из запроса клиента.
- Статус анализа: ложное срабатывание.
- Обоснование и приоритет: низкий. Правило построено на синтаксисе присваивания и срабатывает на корректный код тоже. Основание отклонения проверяемое, достаточно посмотреть сами строки и места передачи параметров.
- Решение и состояние: сохранить код без изменений, проверено повторным прогоном.
- Ответственный и следующий шаг: M1, при следующем прогоне сверить, что сигнал остался на тех же местах и не появился новый.
- Свидетельства: `docs/s09/raw/semgrep-before.json`, `docs/s09/raw/semgrep-after.json`, код `src/NotesApi/NotesRepository.cs`.
- Остаток и пересмотр: сигнал остался и после исправления F-01, тк само присваивание не исчезает. Пересмотреть, если в любое из этих мест начнет попадать значение, пришедшее из запроса или из внешнего файла.

## F-03: MD5 при вычислении ключа кеша

- Источник и версия объекта: Semgrep CE 1.175.0, `docs/s09/raw/semgrep-before.json`, область `src`, commit `1802bbf`.
- Указатель: `weak-hash-md5`, `src/NotesApi/Signals.cs:16`.
- Заявленный риск: слабая хеш-функция в защитной операции, например при хранении пароля или проверке целостности.
- Применимость и достижимость: метод `Signals.CacheKey` вычисляет шестнадцатеричное представление хеша произвольной строки. Поиск по `.cs` файлам репозитория вызовов `CacheKey` не нашел, маршруты в `Program.cs` его не используют. Защитного смысла у ключа кеша в текущем коде нет, пароли и подписи здесь не вычисляются.
- Статус анализа: неприменим в текущем контуре.
- Обоснование и приоритет: низкий. MD5 непригоден там, где нужна стойкость к коллизиям или к подбору, но в заявленном назначении ключа кеша это свойство не требуется. Отсутствие вызовов не делает функцию пригодной для будущего использования, поэтому запись остается в реестре.
- Решение и состояние: сохранить с обоснованием, проверено.
- Ответственный и следующий шаг: M1, при появлении первого вызова заново определить назначение и условия.
- Свидетельства: `docs/s09/raw/semgrep-before.json`, код `src/NotesApi/Signals.cs:14-18`, результат поиска вызовов.
- Остаток и пересмотр: пересмотреть, если `CacheKey` начнет применяться для сравнения или идентификации данных, где важна подмена, или если по ключу будет приниматься решение о выдаче данных. Тогда заменить на SHA-256.

## F-05: System.Random при генерации токена доступа

- Источник и версия объекта: Semgrep CE 1.175.0, `docs/s09/raw/semgrep-before.json`, область `src`, commit `1802bbf`.
- Указатель: `insecure-random`, `src/NotesApi/Signals.cs:30`.
- Заявленный риск: предсказуемый токен доступа позволяет подобрать или воспроизвести чужой токен, те обойти проверку подлинности.
- Применимость и достижимость: метод `NewAccessToken` собирает 16 символов из `new Random()`. По названию и возвращаемому значению это генерация секрета для доступа. `System.Random` не криптографический генератор, последовательность определяется начальным состоянием. Вызовов `NewAccessToken` в репозитории нет, маршруты в `Program.cs` токены не выдают, поэтому в текущем контуре сигнал недостижим.
- Статус анализа: подтвержден по назначению функции, недостижим в текущем приложении.
- Обоснование и приоритет: средний. Нарушается непредсказуемость секрета, а не стойкость хеша, и это свойство нужно именно для токена доступа. Приоритет не высокий только из-за отсутствия вызовов. Отсутствие вызовов это свойство текущего кода, а не свойство функции.
- Решение и состояние: исправить, открыт. Варианты это заменить генератор на `RandomNumberGenerator` из `System.Security.Cryptography` либо удалить неиспользуемую функцию, чтобы ее не подключили в таком виде.
- Ответственный и следующий шаг: M1, вынести решение до переноса процесса на свой проект, в учебном объекте правка не входила в задачу занятия.
- Свидетельства: `docs/s09/raw/semgrep-before.json`, `docs/s09/raw/semgrep-after.json` (сигнал сохраняется, тк код не менялся), код `src/NotesApi/Signals.cs:28-35`.
- Остаток и пересмотр: пересмотреть сразу, как только появится первый вызов, и в любом случае при добавлении в приложение выдачи токенов.

## F-06: фиктивный секрет в истории учебного объекта

- Источник и версия объекта: Gitleaks 8.30.1, `docs/s09/raw/gitleaks-history.json`, конфигурация `.gitleaks-training.toml`, область это отдельная история `../s09-secret-history`, развернутая из `fixtures/secret-history.bundle`, `--log-opts=--all`, режим `--redact`.
- Указатель: `rbpo-training-token`, `demo-settings.env:1`, commit `34d695f7967849875928173c3d4c03c8dc20c52e`. Commit относится к отдельной учебной истории, а не к версии Notes API.
- Заявленный риск: утечка действующих учетных данных через историю репозитория, доступ к внешнему сервису в обход проверки подлинности.
- Применимость и достижимость: сканирование текущего дерева той же истории дало 0 находок и код выхода 0 (`docs/s09/raw/gitleaks-tree.json`, пустой массив), сканирование истории дало 1 находку и код выхода 1. Файл удален коммитом `59a496f`, но остается доступен в истории. Значение фиктивное, формат распознается только учебным правилом, внешнего сервиса за ним нет. Проверка только текущих файлов этот сигнал не дает.
- Статус анализа: подтвержден как факт наличия секрета в истории, в учебном контуре риск отсутствует, тк значение не действующее.
- Обоснование и приоритет: для учебного объекта низкий. Для настоящего секрета приоритет был бы высокий, тк удаление строки новым коммитом не отзывает полномочия и копии истории остаются у всех, кто клонировал репозиторий.
- Решение и состояние: сохранить как учебный пример, проверено. Порядок действий для настоящего секрета: ограничить последствия, отозвать и заменить секрет у его владельца, проверить использование и затронутые сервисы, затем согласованно очищать историю и доступные копии, добавить предотвращающую проверку. Переписывание общей истории в этом упражнении не требуется.
- Ответственный и следующий шаг: M1, при переносе на свой проект использовать штатный профиль правил, профиль `rbpo-training-token` для проекта не подходит.
- Свидетельства: `docs/s09/raw/gitleaks-history.json`, `docs/s09/raw/gitleaks-tree.json`, вывод `git -C ../s09-secret-history log --oneline --all` с тремя коммитами.
- Остаток и пересмотр: вывод ограничен историей примера и одним учебным правилом. Он ничего не говорит о секретах в моем проекте и о других форматах секретов. Gitleaks сообщил `2 commits scanned` при трех коммитах в логе, это число обработанных наборов изменений, а не коммитов.

## F-07: обертка проверки считает пустой результат находкой

- Источник и версия объекта: `scripts/scan-secrets.ps1 -Mode tree` на том же объекте и той же версии, Windows PowerShell 5.1.
- Указатель: строка 28 скрипта, ветка `throw "Unexpected Gitleaks result: exit $code, findings $count."`.
- Заявленный риск: результат проверки может быть истолкован неверно, те ложная находка там, где сканер ничего не нашел.
- Применимость и достижимость: Gitleaks напечатал `no leaks found` и завершился с кодом 0, отчет `gitleaks-tree.json` содержит пустой массив. Скрипт при этом насчитал одну запись и упал. Проверено вручную: `$d = @(Get-Content -Raw .\reports\local\gitleaks-tree.json | ConvertFrom-Json)` дает `$d.Count` равный 1, тип единственного элемента `System.Object[]`, а `$d[0].Count` равен 0. В Windows PowerShell 5.1 пустой JSON-массив приходит одним объектом и не разворачивается, поэтому фильтр по `$null` его не отбрасывает.
- Статус анализа: подтвержден, дефект обертки проверки, а не продукта и не сканера.
- Обоснование и приоритет: для учебного задания низкий, результат сканирования сохранен до падения. В рабочем процессе приоритет был бы выше, тк такая обертка превращает чистый результат в ошибку, а при обратной ошибке могла бы спрятать находку.
- Решение и состояние: учтено, скрипт не изменялся, тк репозиторий учебный и чужой. Фактический результат берется из вывода Gitleaks и из самого отчета.
- Ответственный и следующий шаг: M1, при переносе процесса на свой проект проверять обертку на обоих исходах, пустом и непустом.
- Свидетельства: `docs/s09/raw/gitleaks-tree.json`, вывод скрипта с текстом `exit 0, findings 1`, вывод ручной проверки типов в PowerShell.
- Остаток и пересмотр: поведение проверено только на Windows PowerShell 5.1. На PowerShell 7 разбор JSON отличается, там результат может быть другим, отдельно это не проверялось.
